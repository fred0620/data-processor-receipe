# 設計決策

記錄「為什麼這樣做」，給接手的人看。改變決策時更新這份文件，並在 commit 說明原因。
前半是這個工具自己的決策，後半是共用架構，沒有特別理由不要改。

## 範圍
- pdf-mapper 的下一層：把 PDF 解析出來的資料（或任何 Excel）整理成可以交出去、可以串接的資料表。
- 資料處理需要的邏輯每份資料都不同，所以不把邏輯寫進程式，而是寫在 recipe。程式只提供固定的執行引擎和檢查介面，換資料只換 recipe。
- recipe 由使用者跟自己的 AI 依照 `app/recipe-spec.md` 寫成；AI 不內建在工具裡，工具不連網。
- 不做互動式的「拉欄位、設公式」編輯器。互動只放在檢查和修正：哪裡有疑慮、配對對不對、對照缺什麼。

## recipe 不含程式碼
- recipe 會被分享、會從 AI 直接貼進來，使用者不一定看得懂。如果 recipe 是 Python，載入就等於執行沒人審過的程式；Python 的沙箱很難做得安全。
- 所以 recipe 是 YAML：固定的設定（欄位別名、型別、對照表、配對方式、輸出欄位）加上 SQL 片段。
- SQL 在 DuckDB（MIT）執行。資料由程式先載入，接著關閉外部存取並鎖定設定：SQL 讀寫不到檔案、不能連網、不能安裝或載入擴充套件，也不能把設定改回來。每段 SQL 只允許單一 SELECT 或運算式，超過 120 秒中止。
- SQL 涵蓋大部分整理邏輯：條件判斷、正規表達式、視窗函數、相似度（jaro_winkler、levenshtein）。另外提供 `dp_key`（和程式相同的寬鬆比對鍵）與 `dp_digits`。
- YAML 用自訂的 SafeLoader：YAML 1.1 會把 `on`、`yes`、`no` 當布林值（`on:` 變成 `True:`），這裡只認 true、false。
- 拒絕錨點、別名與所有 `!` 標籤：別名可以用很小的檔案展開成巨大的資料（billion laughs）；標籤是 YAML 被拿來執行程式的入口（`!!python/object/apply`）。recipe 用不到這些，直接禁止，錯誤訊息附行號。
- 不另外接受 JSON：JSON 不能寫註解、SQL 不能換行，對要給人和 AI 一起改的 recipe 不划算。
- recipe 由程式翻成邏輯說明（`engine/explain.py`），不經過 AI，和實際執行的邏輯一致。重點是「一列資料會經過哪些判斷」，不是逐項翻譯設定：以第一個配對的左表為主角，依序寫出讀取、篩選、配對（先找、再找、找到多筆、都找不到）、計算、檢查、輸出，分支寫成「如果／否則」；其他資料表的讀法放在後面，所有欄位的細節預設收起來。SQL 條件做字面替換並附原文。新增 recipe 時先看說明確認再儲存。
- 執行紀錄（`engine/trace.py`）：執行時記下每一格的原始內容、取法、整理、對照（recipe 的或使用者補的）、配對試了哪些方式、哪一步算出來、檢查結果、人工修改。平常不顯示；在單列細節裡，滑到欄位才出現「怎麼來的」，或展開「這一列的處理過程」，才向程式要這一列的紀錄。計算步驟只看得到前後的值，算式要靠 note 與 SQL 原文。
- recipe 檢查一次列出全部問題，訊息寫成「位置：說明」，介面可以一鍵複製給 AI 修正。不認得的設定也會列出來，避免 AI 拼錯字卻被默默忽略。

## 流程
- Load → Gate → Normalize → Match → Transform → Validate → Mapping → Export，每一步在畫面上都有一張卡片顯示結果。
- Load：依別名找表頭，比對不分全半形、大小寫、空白與標點，但必須整格相同，不做模糊比對。必要欄位找不到就停止執行。
- Gate 的條件看 Normalize 之後的值（型別已轉好，寫條件比較直覺），但被排除的列不會產生 Normalize 的警示，畫面順序維持 Gate 在前。
- `sheets` 用萬用字元選工作表（item_*），符合的全部疊在一起，每張各自找表頭；`sheet_column` 把工作表名稱（或其中一段，例如年份）放進欄位。疊起來時列代號是「表:工作表:列」。
- 儲存格取值：`extract` 支援第幾行、關鍵字之後、關鍵字之前、正規表達式，可以列多個寫法依序嘗試（有時候有關鍵字、有時候沒有）。同一格拆多欄用 `source`。跨欄位的條件邏輯放在 transform 的 SQL，inputs 只負責「一格怎麼讀」。
- Normalize 只做明確的轉換。數字接受千分位、貨幣、括號負數、百分比；日期接受常見格式與民國年。判斷不了一律留空、原始內容保留在 raw，顯示在畫面和 Excel，不猜測。
- 數字的小數點符號由 recipe 指定（`decimal: ","` 讀 1.000,02），不自動猜：千分位必須三位一組，1,5 或 1.000,02 在預設設定下會失敗並標記，避免被讀成錯的數字。
- 每一列有 `_rid`（輸入表:Excel 列號），人工決定與警示都靠它對回原始資料。transform 要保留 `_rid`。

## 對照表（Mapping）
- 對照表寫在 recipe：`values`（允許的值）、`entries`（對應值 → 原始寫法）、`missing`（ask、keep、blank）。
- `values` 沒有合適的值時，使用者可以在介面新增對應值（要明確選「新增對應值」，避免打錯字變成新代碼）。新增的值存在本機的對照紀錄，沒有對照在用時自動移除。
- 比對用寬鬆鍵，「空 運」「AIr」不用另外列。
- 用在 inputs 的欄位：值要拿來配對、篩選或計算時。用在 output：只是輸出時要換成代碼。
- `missing: ask` 的值留空並標記，介面的「對照待補」分頁列出所有不重複的原始值和次數，有 `values` 時用下拉選單。補上的對照存在 `workspace/mappings/<recipe>.json`，跟著 recipe 而不是跟著檔案，下次處理其他檔案也會套用，不需要改 recipe。

## 配對方式
- `mode`：one_to_one、many_to_one（預設）、one_to_many、many_to_many。差別在「左表一列可不可以對多列」和「右表一列可不可以給多個左表列」。
- 左表一列可以對多列時，`rows: expand` 每組配對一列（輸出列代號加上右表列代號，仍可各自修改），`rows: combine` 用彙總運算式（sum、string_agg）合成一列。
- 右表一列只能給一個左表列時，同一列被多個左表列選中就拿掉並標記，不替人決定歸屬。
- 人工指定存成右表列代號清單，可以加入、移除；左表一列只能對一列的方式，清單最多一筆。

## 多種比對方式（Match）
- 一個配對可以列出多個方式，依序嘗試，前面配到的列不進入後面的方式。嚴格的放前面、寬鬆的放後面。
- 每個方式可以加 `when`（左表符合條件才用）、`best`（多筆候選時挑最高分）、`review`（配到的要人確認）。
- 只有一筆候選才算配對成功；多筆且分不出高下時標記「多筆候選」，列出前五筆讓人選，不自動挑。`one_to_one` 時，同一個右表列被多個左表列選中，這些都改成待選擇。
- 人工指定的配對與「確定沒有配對」優先於所有自動方式。右表那一列不見了（資料換了），改回自動並提醒。
- 配對畫面左右並列，同名欄位相同時標綠、不同時標橘；沒用到的右表列另外列出。
- 每一列用 `title` 欄位（例如單號）加 Excel 列號辨識；待選擇的候選之間值不同的欄位一定會顯示，候選才不會看起來一模一樣。表和配對用 recipe 的 `label` 顯示，不顯示內部名稱。

## 人工決定
- 警示被人工處理後不刪除，留在畫面上當紀錄：Issue 帶 `resolved`（edited、mapped、matched）與 `note`（改成什麼），視同已確認，不算待處理。流程卡片因此會是藍色的「已處理」，不會變綠色。
- 沒有「重新執行」按鈕：修改、配對、補對照、確認都會自動重算；recipe 更新時，若正在看的結果用的是同一份 recipe，會自動用新版重新處理。檔案內容改了要重新上傳。
- 人工修改、指定配對、確認的警示，存在 `workspace/reviews/<recipe>/<檔案內容雜湊>.json`，跟 recipe 分開。同一份檔案重新執行或改了 recipe 後，決定都還在。
- 修改一律保留原值。輸出欄位直接取自輸入表時，修改在讀進來時就套用，後面的配對、計算、驗證都用修改後的值重算；算出來的欄位只改輸出值。
- 原值和目前資料對不上時（資料或 recipe 改了），保留修改但標記「原始值已變更」。
- 人工改過的格子不再提醒那一格的解析或對照問題；整列的驗證警示仍保留，可以按「確認無誤」。

## 警示
- 跟 pdf-mapper 一樣，警示只標在實際受影響的輸出欄位：輸入欄位的問題經由 `_rid` 和配對帶過來的欄位名稱，對回輸出欄位。
- 同一格已經有解析或對照問題時，不再重複提醒「必填空白」。
- 等級：error（無法執行）、review（需檢查，影響列狀態）、notice（提示，不影響狀態）。

## 輸出
- Excel：整理結果（含檢查狀態、問題說明、來源列；需檢查的格子底色、人工修改加註解）、待檢查、配對明細、排除、對照待補。
- 所有文字儲存格強制文字格式，避免公式注入。

## 介面
- 顏色只有三種意思：綠色是沒問題，橘色是需檢查（找不到用紅色），藍色是人確認或修改過的。流程卡片、列狀態、配對標籤、格子底色都照這個規則。
- 流程卡片、分頁數字、配對的「需處理」都用同一個依據：還沒確認的「需檢查」警示（`_finalize_stages`）。確認後卡片變藍，不會變成沒問題的綠色。每張卡片點開都能跳到相關的列。
- 儲存格可以有多行：預設整理只合併每一行裡的空白，保留換行；結果表預設壓成一行（換行顯示成 ↵），可切換成換行顯示（最多 4 行）；細節的文字欄位會自動長高。
- 原則：簡潔、有空間。字多的地方預設收起來，需要時再展開：流程卡片只放一句摘要，點開看細節；配對卡片先顯示比對用的欄位；結果表可以隱藏欄位、切換緊湊（記在這台電腦的瀏覽器）；警示用一行文字加小連結，不用大色塊。
- 視覺沿用 pdf-mapper 的 Stageshow 樣式（藍 #3b82f6、狀態色橘紅綠），只用系統字型與純 CSS。
- 所有資料用 textContent 放進畫面，不用 innerHTML。
- 分頁：結果（預設只看需檢查）、配對、對照待補、排除、所有警示（可批次確認）。點一列開右側細節，直接修改。

## 套件
- duckdb（MIT）、openpyxl（MIT）、PyYAML（MIT）、Flask（BSD）。避開 AGPL。
- DuckDB 的 Python 自訂函式需要 numpy，所以文字與數字整理在 Python 做、在載入前完成，不註冊自訂函式。

## 共用架構：發布、更新與資料夾分工
- 不包成 exe。PyInstaller 這類打包常被防毒誤判，每次啟動要解壓到暫存，也不能只更新一部分。資料夾加啟動腳本比較透明，IT 也容易審核。
- 資料夾分三塊：`app/` 是程式，更新整包換；`workspace/` 是使用者資料，更新不動；`runtime/` 放 uv、Python 與套件，可隨時刪掉重建。所有路徑集中在 `app/dataprocessor/paths.py`，啟動程式用 `APP_HOME` 指定最外層。
- `run.bat` 只有一行並以 `exit /b` 結尾。cmd 執行批次檔時是一行一行讀，整行讀完才執行，更新時覆蓋 `run.bat` 才不會接著讀到新檔案的內容。
- 發布走 GitLab Release。使用者下載 ZIP 後不用解壓，放進工具資料夾，雙擊 `run.bat` 就會偵測並詢問安裝。不需要共用資料夾，也不用在使用者電腦存 token。
- 不做連網自動檢查；換版步驟寫在附圖解的換版說明，並保留自動換版失敗時的手動做法。
- 只在雙擊開啟時找新版 ZIP；指令列模式不檢查也不暫停，才能放進排程。
- 從網路下載的 ZIP 會被 Windows 標成「來自網路」。第一次安裝要使用者解除封鎖；之後由 `run.bat` 用 PowerShell 解壓安裝，不會再遇到。
- 安裝順序：解壓、確認版本與檔名一致，才把 `app` 改名成 `app.old`、新版移入。中途失敗就換回原狀。保留一份 `app.old` 給使用者自行 `rollback`。
- 啟動程式只會往新版更新；要讓所有人回到舊行為，就發一個還原修改的新版本。
- 發布包附 Windows 64 位元的套件檔（`app/wheels`），用 `uv pip sync` 讓環境和清單完全一致。使用者不需要連到 PyPI，只有第一次要從 GitHub 下載 uv 和 Python（都驗證 SHA256）。
- 版本號只寫在 `app/pyproject.toml`。程式、啟動腳本、CI 都讀它；打標籤時 CI 會比對標籤和版本，CHANGELOG 沒有這一版的段落就不能發布。
- `app/examples/workspace` 的內容只在第一次建立 `workspace` 時放入，使用者刪掉後不會再出現。

## 共用架構：資安原則
- 本機服務只綁 127.0.0.1，只接受 Host 為 127.0.0.1／localhost 的請求（擋 DNS rebinding）；`/api/` 拒絕跨站的 Sec-Fetch-Site 與不符的 Origin（擋 CSRF）。
- 回應加 CSP、X-Frame-Options、nosniff、Referrer-Policy、CORP/COOP；API 回應 no-store。
- 錯誤只回一般訊息，例外細節寫進 `workspace/logs/app.log`。`/api/ping` 只回路徑雜湊，不外洩本機路徑。
- 日誌只記代號與數量，不記檔名與使用者資料的內容。輪替 1 MB × 5 份，30 天以上刪除，外部字串去控制字元。
- 上傳檔案時：檢查檔頭（例如 PDF 要 `%PDF-` 開頭），檔名去掉路徑、控制字元與 Windows 不允許的字元，暫存放 `workspace/uploads`，結束時刪除。
- 輸出 Excel 時：文字儲存格去控制字元並強制文字格式，避免以 `=`、`+`、`-`、`@` 開頭的內容被當成公式。
- 使用者輸入當作檔名或代號時，限制字元與長度，並排除 Windows 保留名稱（CON、PRN、AUX、NUL、COM1–9、LPT1–9）。
- 前端不載入任何外部資源（字型、CDN 套件），公司網路擋外部資源時也能用，也沒有供應鏈風險。

## 共用架構：資源釋放
- 頁面開著時保持一條連線（Server-Sent Events，每 5 秒一次保持訊號）。瀏覽器整個關掉或當掉時來不及通知，但連線一定會斷，工具約 10 秒內就會結束。只靠 heartbeat 時，瀏覽器直接關閉不會送出通知，要等逾時（原本 30 分鐘）才結束；背景分頁的計時器也會被瀏覽器放慢，所以 heartbeat 只當備援（逾時 3 分鐘）。有背景工作時會等工作完成。
- 已開著時再啟動，只開啟原本的頁面，不會多開一份。
- 上傳暫存在結束時清除，異常結束則在下次啟動時清除。

## 治理
- 負責人、備援人、處理的資料與出問題時的做法記在 `OWNER.md`。
- 只留大架構：工具卡、發版檢查清單、維護手冊。不寫各公司不同的政策或登記流程，公司另有規定時以公司為準。
- 每次發版依 `docs/security-checklist.md` 勾選；CI 自動做測試、`uv lock --check`、`pip-audit` 與打包驗證。
- 發布權限：版本標籤設為受保護，只有負責人能建立 Release。

## 待確認
- 外掛：SQL 做不到的邏輯（例如特殊格式解析）要怎麼擴充。方向是另外安裝、經過審查的 Python 外掛，recipe 只能用名字呼叫，不能夾帶程式碼；需要時再加（會用到 numpy）。
- 一列拆多列、多列併成一列（例如一張發票多個品項對多張報關單）：目前用 transform 的 SQL 處理，修改只能改到有 `_rid` 的列。
- 大量資料：寬鬆的相似度比對會讓兩張表互相比較，資料上萬列時要先用等值條件縮小範圍。
- 整份資料層級的檢查（例如總金額要等於某個數）：目前要用 transform 算出來再 validate。
- 真實資料的表頭、髒資料型態，以及跟 pdf-mapper 匯出格式的串接方式。
